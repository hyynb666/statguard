# ML004 — Model Fitted on Test Data

ML004 reports a **potential statistical risk** when a supported scikit-learn
estimator's direct `fit` call receives features or labels that the analyzer can
trace to the test output of a recognized `train_test_split` call. It is enabled
by default and reports at the `fit` call with medium confidence. The finding
does not claim that evaluation occurred, that leakage had a measurable effect,
or that model performance was inflated.

## Required evidence

The rule requires all of the following in one analyzed source scope:

1. Symbol resolution proves an explicit import path for one of
   `sklearn.linear_model.LogisticRegression`,
   `sklearn.linear_model.LinearRegression`,
   `sklearn.ensemble.RandomForestClassifier`, or
   `sklearn.ensemble.RandomForestRegressor`.
2. The receiver at the direct `.fit(...)` call resolves to that constructed
   estimator instance. Aliases are followed at their binding versions; unknown
   calls, receiver mutation, or unsupported signatures cause abstention.
3. A recognized sklearn `train_test_split` precedes the fit call, and supported
   provenance proves that its test-side feature and/or label output is passed
   as `X` and/or `y` to `fit`.
4. The split and fit are in the same module or independently analyzed function
   scope, with straight-line order established by the resolver.

Supported `fit` arguments are positional `X` and optional `y`, or explicit
`X=` and optional `y=` keywords. A single finding is emitted per fit call even
when both test features and labels are used; its explanation identifies which
inputs are test-derived. Independent splits are identified by their source
locations. The adapter accepts a `sample_weight=` keyword to map the supported
signature, but ML004 does not analyze sample-weight provenance. Other keywords,
`**kwargs`, and additional positional arguments cause abstention. The rule does
not infer input roles from names such as `X_test`.

## Examples

Reported because both inputs have proven test roles:

```python
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import train_test_split

X_train, X_test, y_train, y_test = train_test_split(X, y)
model = LogisticRegression()
model.fit(X_test, y_test)
```

Not reported for train-only fitting and ordinary held-out evaluation:

```python
X_train, X_test, y_train, y_test = train_test_split(X, y)
model = LogisticRegression()
model.fit(X_train, y_train)
model.predict(X_test)
model.score(X_test, y_test)
```

`predict`, `predict_proba`, `decision_function`, `score`, and `transform` are
not model-fitting evidence. `partial_fit` is not supported in this version.

## Interpretation and limitations

The observed source pattern shows test-side data entering a model's fitting
operation, so the test set may no longer provide an independent evaluation.
Whether the estimator uses a particular input, whether the code executes, and
the effect on any result remain unknown. Fit using training data and reserve
the test set for final evaluation.

The rule abstains for custom or shadowed same-name classes, unknown estimator
factories and wrappers, unsupported or expanded call signatures, complex
control flow, and unresolved data lineage. Pipeline internals are not expanded.
Module imports used from a function, cross-function or cross-file state, and
cross-Notebook-cell relationships are outside the resolver's supported proof
boundary. Notebook cells are analyzed independently; document order is not
proof of historical execution order. A finding's split location is the source
location of the corresponding split call.

StatGuard parses source and notebook code cells statically. It never imports
scikit-learn, executes submitted Python, runs notebook cells, or analyzes stored
Notebook output content.

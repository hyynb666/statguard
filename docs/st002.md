# ST002 — Discarded Statistical Test Result

## Purpose

ST002 reports a supported SciPy statistical-test result that the statement
clearly discards. The rule identifies a code pattern; it does not claim that a
statistical test is wrong, that discarded output is a bug, or that a p-value
must always be inspected or saved.

## Supported tests and source evidence

The call must resolve through the existing `SymbolResolver` to one of these
exact paths:

- `scipy.stats.ttest_ind`
- `scipy.stats.ttest_rel`
- `scipy.stats.ttest_1samp`
- `scipy.stats.mannwhitneyu`
- `scipy.stats.wilcoxon`
- `scipy.stats.pearsonr`
- `scipy.stats.spearmanr`
- `scipy.stats.chi2_contingency`
- `scipy.stats.f_oneway`

Direct imports, import aliases, module aliases, and simple aliases are
supported when the binding is still resolved at the call site. Calls are not
identified by spelling alone. Custom functions, foreign imports, shadowed or
rebound names, and unresolved wrappers are ignored.

## Trigger patterns

A standalone call discards the result returned by its statement:

```python
from scipy.stats import ttest_ind

ttest_ind(group_a, group_b)
```

The whole result assigned to `_` is also reported. This convention often
expresses deliberate discard, so the finding says so:

```python
from scipy.stats import mannwhitneyu

_ = mannwhitneyu(group_a, group_b)
```

The finding points to the test call. It uses `info` severity, `high` confidence
in the observed syntax pattern, and the `confirmed code pattern` evidence
category. The message is “Discarded statistical test result.” A bare call's
explanation notes that the statistic, p-value, or other result may go
uninspected. For `_ = ...`, the explanation explicitly says that discard may
be intentional. Suggestions use “consider” and are conditional on whether the
output is relevant to the inference.

## Non-trigger patterns

ST002 does not report partial tuple discards:

```python
statistic, _ = ttest_ind(group_a, group_b)
_, pvalue = ttest_ind(group_a, group_b)
statistic, pvalue = ttest_ind(group_a, group_b)
```

The result is not considered discarded when it is assigned normally, returned,
yielded, passed to another function, printed/logged, or used through an
attribute, subscript, condition, or larger expression. ST002 also does not
perform unused-variable or dead-store analysis: an assigned result can remain
unused later without triggering this rule.

## Relationship to ST001 and other rules

ST001 detects a narrower pattern: a supported test's p-value is used in a
literal significance-threshold comparison within a potentially repeated
`for` loop, without observed correction. ST002 does not require a loop,
p-value, threshold, correction analysis, or data provenance. A test call whose
tuple result is unpacked to retain a p-value can trigger ST001 where supported,
but cannot trigger ST002 merely because one tuple element is `_`.

ST002 uses only AST and symbol-resolution evidence; it does not depend on the
ML rules' provenance models. It adds no SciPy or other runtime dependency.

## Limitations

- Only the listed `scipy.stats` APIs and exact resolved bindings are recognized.
- Call results hidden behind wrappers, dynamic dispatch, or unsupported scope
  behavior are not classified.
- Notebook code cells are analyzed independently. Imports in earlier cells
  are not assumed to be present, and stored outputs are not analyzed.
- A finding establishes that a statement discards a supported test result; it
  cannot determine whether the result matters to the author's inference.
- No finding does not establish that all statistical test results are
  appropriately retained or interpreted.

Scanning is static. StatGuard does not import SciPy, execute Python source or
Notebook cells, or inspect Notebook outputs.

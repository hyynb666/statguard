# ML005 — Training-only Evaluation

ML005 reports a **potential statistical risk** when, within one statically
supported scope, a recognized sklearn estimator is fitted on the training
outputs of a known `train_test_split` call and then receives a `.score()` call
on that same split's training features and labels, with no corresponding
held-out `.score()` observed for the same model fit episode.

The Finding is located at the first matching training `.score()` call and cites
the related split location. It says that the model *appears* to be evaluated
only on training data within the analyzed scope. It does not establish that
evaluation was omitted elsewhere, that the model overfit, or that any score is
biased.

- **Severity:** warning
- **Confidence:** medium
- **Evidence category:** potential statistical risk

## Statistical rationale

A score on observations used to fit a model is useful for debugging, model
diagnostics, optimization monitoring, and comparing a train/test gap. It is
not, by itself, an independent estimate of generalization performance. If a
supported scope shows only a training score, consider whether the workflow
also needs evaluation on held-out data or a suitable validation procedure.

## Evidence and supported APIs

- Estimators must resolve to the exact sklearn construction already supported
  by ML004: `LogisticRegression`, `LinearRegression`, `RandomForestClassifier`,
  or `RandomForestRegressor`.
- Split outputs must have explicit `train`/`test` provenance from
  `sklearn.model_selection.train_test_split`.
- The supported fitting call is the estimator's explicit `.fit(X, y)` with
  both inputs proven to be training outputs from the same split.
- The only supported evaluation API is that same estimator instance's
  `.score(X, y)`. Positional and explicit `X=` / `y=` arguments are supported;
  `sample_weight` is accepted but is not used to infer data roles.
- A matching held-out evaluation requires both features and labels to have the
  `test` role from the same split used by that fit episode. Mixed roles, another
  split, or another model do not count as the corresponding evaluation.
- Aliases and reassignment are resolved at each expression's binding version.
  The rule scans the supported scope before deciding whether a candidate is
  suppressed, so a later matching test score prevents an ML005 Finding.
- Repeated training scores for one fit episode produce one Finding. Separate
  estimator instances or later supported fit episodes are tracked separately.

## Example

```python
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression

X_train, X_test, y_train, y_test = train_test_split(X, y)
model = LogisticRegression()
model.fit(X_train, y_train)
train_score = model.score(X_train, y_train)
```

Within this file scope, the pattern can produce ML005. Adding
`model.score(X_test, y_test)` for the same model fit and split suppresses the
training-only Finding.

## Conservative behavior and limitations

- Training scores are not inherently incorrect; they often serve diagnostic
  purposes. ML005 flags only the bounded pattern above.
- A held-out score in another model, another split, or another Notebook cell
  does not suppress this Finding. Notebook cells are analyzed independently;
  document order does not prove execution history.
- There is no cross-file, cross-function, external-helper, or dynamic evaluation
  analysis. A partial file or a dynamic workflow can have evaluation the rule
  cannot see.
- The rule does not interpret `sklearn.metrics`, `predict` followed by a
  metric, arbitrary scoring helpers, or Pipeline internals. It abstains when
  the model is passed to an unresolved helper or an unsupported operation can
  make its state/evaluation unclear.
- `cross_val_score` and `cross_validate` are not treated as a matching test
  score for the fitted instance: sklearn evaluates cloned estimators, and
  cross-validation preprocessing remains ML009's separate concern.
- No source code or Notebook output is executed or inspected for runtime state.

ML005 is a static heuristic, not proof of invalid analysis. Absence of a
Finding does not prove that independent evaluation occurred.

Disable the rule with:

```text
statguard check analysis.py --disable-rule ML005
```

Warnings do not change the default exit code. `--fail-on warning` returns 1
when an ML005 Finding is present.

# ML009 — Potential Preprocessing Leakage Before Cross-Validation

ML009 is distinct from [ML005](ml005.md), which reports a bounded
training-only evaluation pattern. ML009 remains the cross-validation
preprocessing rule.

ML009 reports a **potential statistical risk** when a supported sklearn
preprocessing operation is fitted before a recognized cross-validation call,
and the operation's output is then supplied as that call's `X` input. The rule
does not claim that validation data materially changed learned parameters,
model behavior, or scores.

## Required evidence

All of these facts must be established within one parsed Python unit and one
supported straight-line scope:

1. Symbol resolution identifies `sklearn.model_selection.cross_val_score` or
   `sklearn.model_selection.cross_validate` at the downstream call.
2. The `X` argument is unambiguous: positional argument 2 or keyword `X`.
   Starred arguments, `**kwargs`, duplicate names and ambiguous bindings are
   rejected.
3. Provenance follows the `X` value through known binding/alias edges to an
   explicit supported transform output. Arbitrary wrappers do not preserve
   lineage.
4. The transform occurs before the CV call in the same scope, and the original
   transformer construction, fit configuration, input and object identity are
   supported by the existing sklearn provenance adapter.
5. Existing component semantics confirm that fitting learns data-dependent
   preprocessing behavior. In particular, ML002 and ML003 configuration
   checks are reused rather than reimplemented.

The Finding points to `fit_transform` or the separate `fit` call. Its
explanation also identifies the downstream CV API and location. If one
preprocessing output reaches two separate CV calls, each downstream validation
context receives a Finding; exact duplicates remain deduplicated by Analyzer.

## Supported APIs and components

Cross-validation functions:

- `sklearn.model_selection.cross_val_score`
- `sklearn.model_selection.cross_validate`

Direct imports, callable aliases and module aliases are accepted when the
resolved import binding remains unshadowed. Namesakes, dynamic lookup, custom
wrappers and module-level names referenced from function bodies are not assumed
to refer to sklearn.

Preprocessing semantics are delegated to existing helpers:

- Scalers: `StandardScaler`, `MinMaxScaler`, `RobustScaler`.
- Imputers: `SimpleImputer` with supported data-dependent strategies,
  `KNNImputer`, and `IterativeImputer` with the existing `max_iter` and
  `initial_strategy` constraints. An explicitly fixed constant-only
  `SimpleImputer` strategy is not reported.
- Feature selectors: `SelectKBest`, `SelectPercentile`, and
  `VarianceThreshold`, subject to ML003's score-function, target and no-op
  checks. `VarianceThreshold` is described as using empirical feature variance,
  not labels.

Both `fit_transform(X)` and a proven same-instance `fit(X)` followed by
`transform(X)` are supported. Separate calls require matching stable input
binding versions and explicit order. For example, a function parameter is a
known local binding; an unresolved value returned by a dynamic call may not be.

## Risk example

```python
from sklearn.model_selection import cross_val_score
from sklearn.preprocessing import StandardScaler

scaled = StandardScaler().fit_transform(X)
scores = cross_val_score(model, scaled, y, cv=5)
```

The scaler's fitting statistics were computed before the CV procedure split
the supplied rows into training and validation folds. Validation-fold
observations may therefore have influenced those statistics.

The separate form is supported when the input binding and object state can be
proven, for example inside a function with local imports:

```python
def evaluate(X, y, model):
    from sklearn.model_selection import cross_val_score
    from sklearn.preprocessing import StandardScaler

    scaler = StandardScaler()
    scaler.fit(X)
    scaled = scaler.transform(X)
    return cross_val_score(model, scaled, y, cv=5)
```

## Pipeline boundary

The following is not reported because raw `X` is passed to cross-validation;
the estimator argument is an sklearn Pipeline whose steps are fitted by sklearn
within each training fold:

```python
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

pipe = make_pipeline(StandardScaler(), model)
scores = cross_val_score(pipe, X, y, cv=5)
```

Pipeline is one way to place preprocessing within fold training. It does not
prevent every possible form of leakage, and ML009 does not inspect Pipeline
internals. If already-preprocessed data is passed as `X`, an estimator Pipeline
does not erase evidence that the external preprocessing happened first.

## Finding semantics

- Rule: `ML009`
- Severity: `warning`
- Confidence: `medium`
- Evidence: `potential statistical risk`

The message is intentionally qualified. A Finding establishes a supported
source pattern, not a measured effect. No Finding does not establish that CV is
free of leakage; unsupported calls, external helpers and unknown data lineage
remain outside the analysis.

## Boundaries and safety

ML009 does not support `GridSearchCV`, `RandomizedSearchCV`,
`cross_val_predict`, learning/validation curves, arbitrary CV wrappers, or
dynamic estimator/data access. It checks the `X` argument only, not a
preprocessor output supplied only as `y`. It does not infer data preservation
through arbitrary calls, branches, loops, in-place mutation, cross-function,
cross-file, or cross-Notebook-cell relationships. A transform without known
same-instance fitting is not reported. An unresolved dynamic CV or
preprocessor call is not treated as a supported library API.

Notebook cells are analyzed independently; document order is not proof of
historical execution order. Notebook output is not analyzed. The implementation
uses AST/import/provenance evidence only and never imports sklearn, executes
source or cells, or adds a runtime dependency. Scanning code remains static and
does not access a notebook kernel or network.

Run and disable the rule:

```text
statguard check analysis.py
statguard check analysis.py --disable-rule ML009
statguard check analysis.py --format json --fail-on warning
```

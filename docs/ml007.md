# ML007 — Test Data Used for Model Selection

## Purpose

ML007 reports a potential statistical risk when a recognized scikit-learn
model-selection search is fitted using data that StatGuard can trace to the
held-out output of an earlier `train_test_split` call. Search results can depend
on the supplied data; using a held-out partition for candidate selection may
mean it is no longer an independent final evaluation set if it is reused for
that purpose.

The Finding is a review prompt. Static source analysis cannot establish whether
the same partition is later presented as a final test set, whether another
independent evaluation set exists, or how large any resulting bias might be.
It does not assert that the analysis is invalid or that model performance is
overestimated.

## Trigger and evidence

ML007 requires all of the following within one supported module or function
scope:

1. The search constructor resolves exactly to
   `sklearn.model_selection.GridSearchCV` or
   `sklearn.model_selection.RandomizedSearchCV`.
2. The exact search instance is not reassigned or passed to an unresolved call
   before the reported `.fit()`.
3. An unambiguous `.fit()` call occurs after a supported
   `sklearn.model_selection.train_test_split` call in that scope.
4. At least one explicit `.fit()` feature (`X`) or target (`y`) input has
   `test` role provenance from that split.

This is classified as **potential statistical risk**, with `warning` severity
and `medium` confidence. The diagnostic points to the search `.fit()` call and
includes the split location as supporting context. A feature input, a target
input, or both can establish the risk; one `.fit()` emits one Finding.

## Supported APIs and calls

The exact supported search paths are:

- `sklearn.model_selection.GridSearchCV`
- `sklearn.model_selection.RandomizedSearchCV`

Import aliases, module aliases, `from sklearn import model_selection`, simple
constructor aliases, and direct constructor chaining are supported when the
existing SymbolResolver can prove the same constructor identity. The search
object's own `.fit()` is the only triggering method.

The first two positional inputs are interpreted as `X` and optional `y`.
Keyword forms `X=...` and `y=...`, including mixed positional/keyword calls,
are supported. Other named fit metadata such as `groups` is ignored. Expanded
`*args`, `**kwargs`, duplicate keywords, duplicate positional/keyword `X` or
`y`, and calls without an explicit `X` input are ambiguous and are not
reported. Constructor parameter grids/distributions, `cv`, and `refit` values
are not inspected; their values do not change this rule's input-provenance
requirement.

## Positive example

```python
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import GridSearchCV, train_test_split

X_train, X_test, y_train, y_test = train_test_split(X, y, random_state=42)
search = GridSearchCV(LogisticRegression(), {"C": [0.1, 1.0, 10.0]})
search.fit(X_test, y_test)
```

The rule does not rely on the spelling `X_test` or `y_test`: these values must
have been assigned from the recognized split's test-role outputs. It also
accepts a test-role alias such as `heldout = X_test`.

The Finding states that test features and labels enter the recognized search
fit. This establishes use in model selection, not later reuse as an allegedly
independent final test set.

## Safe negative example

```python
search = GridSearchCV(LogisticRegression(), {"C": [0.1, 1.0, 10.0]})
search.fit(X_train, y_train)
search.score(X_test, y_test)
```

Fitting the search on training-role data does not trigger ML007. A subsequent
`.score()` or `.predict()` on test data is not a model-selection fit and does
not trigger it either. Normal GridSearchCV cross-validation over training data
is not itself a violation.

## Aliases, rebinding, scope, and unknown behavior

Point-of-use bindings and existing provenance records determine data role.
Rebinding a test alias to training data or rebinding a search variable to a
custom object does not reuse stale evidence. If the search object is passed to
an unresolved call or another method is called on it before the target `.fit()`,
the rule conservatively abstains because its identity or state may have
changed. Custom same-name classes/functions, factory-wrapped search objects,
unresolved imports, and unknown split helpers are not recognized.

The split must precede `.fit()` in the same statically supported scope. No
cross-function, cross-file, or cross-Notebook-cell provenance is inferred.
Notebook code cells are analyzed independently; cell document order is not
proof of historical execution order. Submitted Python/Notebook code is never
executed, and stored Notebook outputs are not analyzed.

## Suppression and CLI

ML007 is enabled in the development default registry and can be disabled with
`--disable-rule ML007` or `[tool.statguard].disable-rules = ["ML007"]`. Inline
suppression follows the shared Analyzer policy:

```python
search.fit(X_test, y_test)  # statguard: ignore ML007
```

As a warning, it does not change the default CLI exit status. An explicit
`--fail-on warning` threshold applies unless the Finding is suppressed.

Console, JSON schema 1.0, offline HTML, and SARIF 2.1.0 reporters consume the
same Finding model; the rule adds no reporter-specific behavior or runtime
dependencies.

## Known limitations

ML007 does not detect:

- Hand-written model or hyperparameter loops, or arbitrary score comparisons.
- `cross_val_score`, `cross_validate`, validation/learning curves, nested-CV
  correctness, or `HalvingGridSearchCV`/`HalvingRandomSearchCV`.
- Search APIs from Optuna, Ray Tune, Hyperopt, XGBoost, LightGBM, custom
  libraries, or custom wrappers.
- Pipeline internals, cross-file/cross-cell search, or later reuse of a test
  partition outside the analyzed scope.
- Whether the user has a separate final evaluation set, whether a test set is
  subsequently reused, or the amount/direction of any performance bias.

Unknown control flow, dynamic calls, ambiguous fit arguments, and unresolved
object mutation cause the rule to abstain. No Finding does not establish that
model selection is statistically safe.

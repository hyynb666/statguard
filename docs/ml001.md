# ML001 — Potential Preprocessing Leakage

Default severity: warning. Confidence: medium. Evidence category: potential
statistical risk. Enabled by default in the CLI's built-in registry.

## Evidence and statistical rationale

The rule requires all of the following:

1. The receiver comes from an explicit public sklearn.preprocessing.StandardScaler,
   MinMaxScaler or RobustScaler construction, resolved through imports and aliases.
2. A supported fit_transform call learns preprocessing parameters. StandardScaler
   with both with_mean/with_std disabled and RobustScaler with both
   with_centering/with_scaling disabled abstain. Unknown learning switches and
   expanded constructor options also abstain.
3. That call's output reaches an exact sklearn.model_selection.train_test_split
   input through versioned aliases or supported transformation edges.
4. SymbolResolver records the fitting call before the split in the same supported
   module or function-local evaluation scope. Textual row order alone is not proof.
5. The path does not cross a prior train/test partition or an opaque return value.

Scalers estimate parameters from their fitting input. If that transformed data
is subsequently partitioned, eventual test observations may have influenced those
parameters. This is potential risk, not proof of actual leakage, inflated scores
or statistical significance. The observation is conditional on successful
execution of the declared APIs. It follows sklearn's guidance to split before
fitting preprocessing and to use appropriately configured training pipelines:
[common pitfalls](https://scikit-learn.org/stable/common_pitfalls.html),
[StandardScaler](https://scikit-learn.org/stable/modules/generated/sklearn.preprocessing.StandardScaler.html),
[MinMaxScaler](https://scikit-learn.org/stable/modules/generated/sklearn.preprocessing.MinMaxScaler.html),
[RobustScaler](https://scikit-learn.org/stable/modules/generated/sklearn.preprocessing.RobustScaler.html).

## Example

```text
from sklearn.preprocessing import StandardScaler
from sklearn.model_selection import train_test_split
scaler = StandardScaler()
scaled = scaler.fit_transform(X)
train, test = train_test_split(scaled)
```

```text
statguard check analysis.py
statguard check analysis.py --format json
statguard check analysis.py --fail-on warning
statguard check analysis.py --disable-rule ML001
```

The warning points to the fit_transform call on line 4, column 10. Its explanation
records the corresponding split location on line 5. Notebook diagnostics include
both original cell_index and code-cell ordinal. Console and JSON share Finding.
Default warnings exit 0; --fail-on warning exits 1; scan errors still exit 2.

## Supported and negative cases

Import aliases, module aliases, callable/receiver aliases, direct constructor
chains, simple output aliases, nested fit_transform inside split, and independent
problems are supported. Each fit/split pair yields one Finding; duplicate array
arguments or repeated checks do not duplicate it. Separate splits retain distinct
related locations. A new binding does not change the data an old alias represents.

Split-first train-only fitting, normal Pipeline use, unrelated split inputs,
replaced result bindings, user-defined names and unknown wrappers abstain. Merely
seeing fit_transform and train_test_split is insufficient. Already partitioned
inputs are not reclassified as full input, even if later split again.

Before fitting, unmodeled methods on the same receiver or passing that receiver
to another call may change configuration, so the rule abstains. Rebinding to a
new constructor creates a distinct receiver. This is a conservative guard, not
an object state engine. Opaque library monkey-patching and nonstandard imports
remain outside the declared-import model.

## Explicit limits

Separate fit(X) then transform(X) is **not supported**. Current provenance tracks
creation and output relationships, not reliable fitted-object state. That pattern
and fit-return-self chains have negative tests. This is a first-version subset
of the eventual PRD ML001 scope, as allowed by Issue #9; absence of a finding is
not evidence of safety. Imputers and supported feature selectors are handled by ML002 and ML003; Pipeline internals and other transformers remain unsupported.

Module-level imports used inside functions remain unknown; explicit local imports
work. Branches, loops, dynamic lookup, arbitrary factories, subclasses, starred
arguments, unsupported signatures, mutation and cross-function/file/cell data flow
remain conservative. Some valid programs therefore receive no warning. Notebook
cells are independent and document order is not historical execution order.

The rule reports no data contents and never imports/executes scanned source or
reads Notebook outputs. No runtime third-party dependency is required.

## Integration and compatibility

`statguard.rules.default_registry()` returns a fresh registry containing ML001, [ML002](ml002.md), and [ML003](ml003.md).
`Analyzer(registry)` still honors the caller's exact registry; an explicitly empty
registry remains empty. CLI --disable-rule RULE_ID is repeatable, uses registry
selection and rejects unknown IDs. If a registry is explicitly injected into
CLI main, disabling updates that registry's selection. Registration/disable do
not execute rules. JSON schema and Finding interfaces are unchanged.

`SymbolResolver.evaluation_site(expr)` returns an immutable scope/order record
for supported expressions, or None outside coverage. Calls are recorded after
callee and arguments, making nested evaluation order explicit. Compare order
only within the same scope; it does not prove invocation order across functions.

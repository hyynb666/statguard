# ML002 — Potential Imputation Leakage

ML002 reports a statically proven code pattern with a **potential statistical
risk**. It is enabled by default. The finding does not assert that leakage
actually occurred, that test samples changed learned values, or that model
performance is biased.

## Required evidence

The rule emits a warning only when all these facts are established in one
supported straight-line scope:

1. Symbol resolution identifies an exact public construction of
   `sklearn.impute.SimpleImputer`, `KNNImputer`, or `IterativeImputer`.
2. The instance receives `fit_transform(X)`. For `SimpleImputer`, its
   strategy is statically known as the default/`"mean"`, `"median"`, or
   `"most_frequent"`.
3. Provenance traces that exact transformed output, optionally through simple
   aliases, into a later resolved
   `sklearn.model_selection.train_test_split`.
4. Evaluation sites prove the fit occurs before the split in the same scope.
   The receiver is the same constructor object and has not been passed to an
   unknown call or changed through an unmodeled method in between.

The warning points to `fit_transform`; its explanation includes the related
split location. Distinct fit/split evidence pairs remain distinct, while exact
duplicates are removed by the Analyzer.

## Statistical meaning

The supported imputers learn different information:

- `SimpleImputer(strategy="mean")`, `"median"`, and `"most_frequent"`
  learn a per-column statistic from fitting data.
- `KNNImputer` retains fitted reference samples and uses neighboring samples
  to fill missing values.
- `IterativeImputer` fits iterative estimation models using relationships
  among features.

When the fitted output is later divided, observations that eventually become
held-out data may have influenced that learned operation. The usual correction
is to split first, fit on training data, and transform validation/test data
with the fitted object. A correctly configured sklearn Pipeline within the
training workflow is another appropriate boundary.

`SimpleImputer(strategy="constant")` uses a fixed replacement and is not
reported. Callable, dynamic, `**kwargs`, or unknown strategy values are also
not reported because their data dependence is not statically established.
This conservative abstention is not a claim of safety.

## Supported syntax

Imports, module aliases, imported-name aliases, callable aliases, direct
constructor chains, receiver aliases, transformed-output aliases, nested
`fit_transform` inside the split call, and multiple independent operations
are supported when their existing SymbolResolver and Data Provenance facts are
known. Reassignment uses the binding at each expression's actual use site.

The customary experimental enable statement is accepted as ordinary syntax:

```python
from sklearn.experimental import enable_iterative_imputer
from sklearn.impute import IterativeImputer
```

StatGuard never imports sklearn or executes that statement. It recognizes only
the declared public `sklearn.impute.IterativeImputer` source. This keeps
analysis independent of the installed sklearn version while preserving the
common experimental API form.

## Examples

Reported:

```python
from sklearn.impute import SimpleImputer
from sklearn.model_selection import train_test_split

imputer = SimpleImputer(strategy="median")
filled = imputer.fit_transform(X)
X_train, X_test = train_test_split(filled)
```

Not reported because the split is first and fitting is train-only:

```python
X_train, X_test = train_test_split(X)
imputer = SimpleImputer(strategy="median")
X_train = imputer.fit_transform(X_train)
X_test = imputer.transform(X_test)
```

Not reported because replacement is explicitly constant:

```python
imputer = SimpleImputer(strategy="constant", fill_value=-1)
filled = imputer.fit_transform(X)
X_train, X_test = train_test_split(filled)
```

Run or disable the rule:

```text
statguard check analysis.py
statguard check analysis.py --disable-rule ML002
statguard check analysis.py --format json --fail-on warning
```

Warnings exit 0 by default. `--fail-on warning` exits 1 for ML002. ML001 and
ML002 can be disabled independently.

## Known limits and safety

Separate `fit(X)` followed by `transform(X)` is not supported because
current provenance does not model estimator fit state. Pipelines, arbitrary
wrappers, subclasses, factories, positional constructor arguments, dynamic
calls, starred arguments, complex control flow, module globals referenced from
functions, and cross-function/file/Notebook-cell data flow are outside this
version. Notebook cells are analyzed independently and document order is not
historical execution order.

ML002 does not recognize pandas `fillna`, custom helpers, or other imputers.
Names such as `imputer`, `fit_transform`, `X_train`, or a coincident
custom class never establish library identity or lineage. Unknown or invalid
runtime configurations can therefore produce no warning.

The implementation is fully static. It does not import sklearn, run source,
execute Notebook cells, inspect Notebook output, use a kernel, or access a
network service. It reuses the existing SymbolResolver, Data Provenance graph,
AnalysisContext, Analyzer, Finding, and default RuleRegistry. No runtime
dependency or report schema change is introduced.
